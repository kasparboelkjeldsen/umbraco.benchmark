Why MCP Makes Your CMS Talk Back

This very site was modelled, filled and published by an AI assistant talking to Umbraco over MCP. Here's what that feels like, and why it matters.

Here's a confession: nobody clicked through the Umbraco backoffice to build this blog. The document types, the block grid, the media library and the very words you're reading were all created by an AI assistant calling Umbraco's MCP servers, one well-described tool at a time.

That's not a party trick. It's a glimpse of how content management changes when your CMS can explain itself to an assistant: what types exist, what a property expects, which pages are live. The assistant stops guessing and starts asking the system directly.

Two servers, two jobs

This project runs two MCP servers side by side. One is for developers: it creates data types, document types, templates and media. The other is for editors: it creates pages, adds blocks and publishes. Splitting them means each assistant only sees the tools that fit its role, and an editor's assistant can't accidentally redesign the schema.

  • Self-describing: a tool can hand back the exact JSON shape a media picker expects, so nothing is guessed.
  • Safe by default: drafts stay drafts until something explicitly publishes them.
  • Verifiable: every write can be read straight back to confirm it landed.

Conventions still win

Giving an assistant access is only half the story. This project has firm conventions: where document types live, how blocks render, how files are named. MCP doesn't replace them. Instead the assistant follows them, because the tools make the right way the easy way.

The result is a CMS you can talk to without it turning into a mess. Ask for a blog, get a blog, and still recognise the codebase the next morning. That, more than any demo, is why MCP is awesome.
