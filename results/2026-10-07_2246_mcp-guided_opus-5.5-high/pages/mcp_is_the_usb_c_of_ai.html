MCP Is the USB-C of AI

One standard plug instead of a drawer full of adapters: why the Model Context Protocol makes connecting AI to your tools boring in the best possible way.

Remember the drawer? The one full of chargers, each with a slightly different plug, each fitting exactly one device you no longer own. For years, connecting an AI model to your own tools felt just like that drawer. Every assistant needed its own bespoke integration, every API needed its own glue code, and every new model meant starting over.

The Model Context Protocol (MCP) is the moment the industry agreed on a single plug. A tool author writes one MCP server, and any MCP-capable client (a chat app, an IDE, a coding agent) can use it straight away. That's the whole trick, and it turns out to be a very big trick.

Write once, plug in everywhere

Before MCP, connecting M models to N tools meant building M × N integrations. With a shared protocol it becomes M + N: each tool exposes one server, each client speaks one protocol, and they meet in the middle. Tool authors get reach, client authors get an ecosystem, and users get to pick both freely.

MCP servers describe their own capabilities: tools with typed inputs, resources to read, prompts to reuse. A client doesn't need to be taught what a CMS, a database or a ticketing system can do; it asks the server, and the server tells it in a format every client understands.

Boring, in the best way

The highest compliment you can pay a standard is that people stop talking about it. Nobody gets excited about plugging in a USB-C cable; it just works. MCP is heading the same way: once your tools speak it, connecting a new assistant is a configuration line, not a project.

That frees everyone to focus on the interesting part: what the assistant actually does with the access it now has. Which is exactly where the fun starts.
