Why MCP is awesome: tools that actually fit the job

The Model Context Protocol turns a chat assistant into something that can actually do the work — here is what that feels like when you build a whole site through it.

The Model Context Protocol (MCP) is the reason this very site exists. Not a theme, not a plugin — a whole content model, pages, images and all, assembled by an agent talking to Umbraco over MCP. Before MCP, an assistant could only talk; with MCP it can do: create document types, publish pages, upload media, assign domains. The tools are not bolted on afterwards — they are the interface.

What makes MCP elegant is that one protocol works everywhere. The Umbraco MCP server exposes the CMS's own management API as tools; an editor MCP server does the same for content. One agent, two servers, zero custom glue code. The model never scrapes a backoffice or guesses at an endpoint — it calls a named tool with typed arguments and gets structured results back.

There is a quiet benefit to tool-driven work: every step is verifiable. Each call returns a real id, and each id can be read back. When a schema write lands, you fetch the document type and confirm the properties; when a page is created, you fetch the page and check the values. Nothing is taken on faith, and nothing fails quietly — a bad payload comes back as an error that says exactly what to fix.

It also keeps the architecture honest. Because the agent must go through Umbraco's own APIs, the conventions of the platform — document type folders, compositions, block grids — are enforced by the CMS itself rather than by prompt instructions. The result is a site that looks exactly like one built by hand in the backoffice, because in every way that matters, it was.

“MCP turns "please update the site" from a hope into a workflow: named tools, typed arguments, verifiable results.”

— the whole reason this blog exists
