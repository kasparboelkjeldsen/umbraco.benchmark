Why MCP is awesome: one protocol, every tool

Before MCP, every integration was a bespoke cable. Now there is one plug both sides speak — and the content stack is no exception.

Photo: Lucian Alexe / Unsplash

Every integration used to be a bespoke cable: a custom connector for the CMS, another for the CRM, another for analytics. Each one had to be designed, built, and maintained on both ends. MCP replaces that tangle with a single, open protocol — one plug that both sides already speak.

The M×N problem

Think of the old state of affairs as an M×N problem: M applications that each want to reach N tools and data sources. Without a shared protocol, the only answer was custom integrations — M×N bespoke cables, each one its own little project with its own auth quirks, its own data shapes, its own failure modes. It is the same reason USB replaced a drawer full of proprietary chargers.

MCP collapses that to M+N: an application implements the protocol once, a tool server implements it once, and they can talk. New tool? Plug it in. New client? It already knows how to listen.

Why it matters for content

For a CMS, this is quietly a big deal. An MCP server exposes the content model — document types, media, publishing — as tools and resources, so anything from an editor's assistant to a build pipeline can work with the same well-defined surface. The value is not that the protocol is clever; it is that it is boring: standard, open, and already implemented everywhere. That is exactly what a protocol should be.
